# Design note (one page)

**Workflow.** A single Python chat agent calls a real Anthropic model for request understanding and tool choice. LangGraph is deliberately narrow: it checkpoints an action ID, interrupts for approval, then resumes the action. SQLite stores conversation facts, preferences, mock provider records, and a separate action ledger. The graph checkpoint handles pause/resume; the action ledger is the source of truth for side effects. This adds one state layer, but keeps provider safety independent of LangGraph. No extra agents or external services are needed.

**Approval and recovery.** `ActionDispatcher.propose` freezes action type, user, provider, booking/hold ID, slot and displayed price, and persists a stable idempotency key before any provider call. Only application code can approve that exact JSON proposal. Changing material details clears approval; pending actions cannot be changed. A repeated confirmation returns the durable outcome. On a booking timeout, the dispatcher queries `get_booking_status` before claiming success. If status lookup also fails, it leaves the action pending; after restart it checks status again with the same key before any provider call. The mock provider also deduplicates on the key. Cancellation retries one simulated 503 with its same key; reschedule conflict preserves the original slot.

**Memory and untrusted input.** Preferences have user scope and explicit/inferred provenance. Unconfirmed inferred and forgotten facts never enter prompt context. Old chat is omitted so it cannot reintroduce a forgotten fact; current structured facts preserve the active request. The model sees relevant confirmed preferences within a 4 KB selected-context cap; the entire request payload is also capped before each model call. Provider reviews are untrusted. The dispatcher validates held slot, budget, account booking and exact approval in code. Model prose cannot announce booking success; the agent renders outcomes from verified state.

**Observability and evaluation.** JSONL records model calls, usage, estimated cost when available, tool arguments and sanitized results, latency, context sent, action transitions and final outcomes. `EVAL_TABLE.md` is generated by 33 offline simulated-user scenarios; unit tests cover restart and contract details. The model is used live only when a local API key is supplied. The local page shows chat and trace side by side on `127.0.0.1`.

**Annotated trace.** The raw end-to-end file is `TIMEOUT_TRACE.txt`. Its `proposed` event shows the frozen provider, slot, price and hold; `approved` precedes `book_call`; `booking_timeout` records the lost acknowledgement; `status_checked` returns `confirmed` using the same idempotency key; only then does `confirmed` emit the user-facing success message. The provider-side count was one booking and one booking call.
